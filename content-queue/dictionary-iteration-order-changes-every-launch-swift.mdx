A test failed on CI. I reran it and it passed. I reran it again and it failed. Nothing had changed.

The test compared two JSON strings. The JSON was built from a `Dictionary`. And Swift, it turns out, had been quietly reshuffling that dictionary between every process launch for years without me ever noticing.

This isn't a bug. It's a documented security feature, and once you know it's there you start spotting the places you accidentally depended on it.

---

## Swift picks a new hash seed every time your app starts

`Dictionary` and `Set` are hash-based. An element's position in the underlying storage comes from its hash value, and iteration walks that storage in order. So iteration order is a function of the hash values.

The part that surprises people: **Swift's hasher is seeded with a random value chosen once per process.** The same `Dictionary`, built from the same keys in the same order, iterates differently in two consecutive launches of the same binary.

```swift
let scores = ["alice": 10, "bob": 20, "carol": 30]
for (name, _) in scores { print(name) }

// Launch 1: bob, alice, carol
// Launch 2: carol, bob, alice
// Launch 3: alice, carol, bob
```

The reason is hash-flooding defense. If an attacker knows your hash function exactly, they can craft thousands of keys that all collide into one bucket, turning your O(1) dictionary into an O(n) linked list and your server into a space heater. It's a real attack class that hit a lot of languages in the early 2010s. Per-process seeding makes it impossible to precompute collisions against a specific run.

Swift is also upfront about this. The documentation never promises an iteration order for `Dictionary` or `Set` — they're explicitly unordered collections. It's just that "unordered" reads like "arbitrary but probably consistent," and it means something much stronger here.

## Where this actually hurts

Random order is harmless for the thing dictionaries are for: looking up a value by its key. The damage is always in code that *iterates* and then treats the result as meaningful.

**Flaky tests.** The original sin. You build an expected string from a dictionary, or compare two arrays produced by mapping over a `Set`. Passes locally twenty times, fails on CI, passes on rerun. This is the single most common way people discover the behavior — and because it's a 1-in-n chance per run, it looks like infrastructure flakiness rather than a real bug in your assumptions.

**Cached signatures and ETags.** This one is nastier because it ships. Serialize a dictionary to JSON, hash the string, use it as a cache key or an idempotency token. Now your "unchanged" payload produces a different hash on every launch, so your cache never hits and your dedupe logic never dedupes. The app works, just with a cache that silently does nothing — the worst kind of broken.

**Golden-file tests.** Snapshot a serialized model containing a dictionary and the recorded file is only valid for the process that wrote it.

**UI that looks fine in review.** A `ForEach` over `Dictionary` values with no sort. In the simulator it's a list of five items in *some* order and nobody questions it. In production, users relaunch the app and their settings list has reshuffled itself. The bug report reads "the order keeps changing randomly," which is accurate, correct, and will be dismissed as a user being confused.

There's a related trap worth naming: taking an *offset* from `enumerated()` over a dictionary and treating it as a stable position. That one's bad for two reasons at once, and I've written about [why `enumerated()` gives you an offset and not an index](/blog/enumerated-offset-is-not-an-index-swift) separately.

## The fix is to sort, and to mean it

There's no flag that makes production dictionaries ordered, and you don't want one. The fix is to impose an order at the point you need one.

```swift
// Unstable: order is whatever this process's seed produced
let keys = Array(scores.keys)

// Stable: an explicit, reproducible order
let keys = scores.keys.sorted()

// Serializing? Sort first, then build.
let json = scores.sorted { $0.key < $1.key }
                 .map { "\"\($0.key)\":\($0.value)" }
                 .joined(separator: ",")
```

For `JSONEncoder` specifically, there's a flag that does this for you:

```swift
let encoder = JSONEncoder()
encoder.outputFormatting = [.sortedKeys]   // deterministic key order
```

If you're hashing encoder output for a cache key or an idempotency token, `.sortedKeys` is not optional. Set it.

And if the order *is* part of your data model — insertion order matters, positions are meaningful — then a dictionary was the wrong type. Use an `Array` of pairs, or an array of keys alongside the dictionary for lookup. Encoding order into a type that explicitly doesn't preserve it is a losing fight.

---

## Make the flakiness stop being random

This is the part most people don't know exists. You can turn off the random seeding:

```bash
SWIFT_DETERMINISTIC_HASHING=1
```

Set it as an environment variable and the hasher uses a fixed seed, so iteration order becomes consistent across runs of that process. Add it to your test scheme's environment variables, or your CI job.

Be clear about what this buys you, though, because it's easy to misuse. It makes order-dependent tests **reproducible**, not **correct**. A test that passes only under deterministic hashing is still asserting something your production code doesn't guarantee — you've converted a flaky test into a reliably-passing test that's still wrong.

Use it the other way around: as a debugging tool. When a test is flaking and you suspect hash order, setting it proves the diagnosis in one run instead of twenty. Then go fix the test to sort, and the variable stops mattering.

It's also handy inverted. Leaving it *off* in CI is a feature — it means your suite is continuously probing for accidental order dependence, a few percent of the time, for free. The flaky test isn't the problem. It's the only reason you found out.

## The pattern underneath

Swift's standard library is full of contracts that are narrower than they look, and the dangerous ones are the ones your code satisfies by accident.

[`sorted()` makes no promise about equal elements](/blog/swift-sorted-is-not-a-stable-sort) — and happens to be stable in the current implementation, so testing confirms a guarantee that isn't in the contract. [A hash that changes after insertion corrupts the `Set` holding it](/blog/mutating-hashable-class-corrupts-set-swift). [`NSCache`'s limits are hints, not caps](/blog/nscache-not-a-dictionary-with-a-limit). Same shape every time: the observed behavior is stricter than the documented behavior, you build on the observation, and the gap closes on you at an inconvenient moment.

Hash order is the friendliest member of that family, because it breaks *constantly* and loudly instead of waiting for a toolchain upgrade. Every flaky dictionary test is the runtime telling you the truth. If you want the habit of writing tests that pin real contracts instead of incidental behavior, the [Swift Testing lesson](/learn/swiftui-in-practice-15-swift-testing-view-models) goes at it properly.

If order matters, say so in code. A `Dictionary` will never say it for you.
